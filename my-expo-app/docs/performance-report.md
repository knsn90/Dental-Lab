## 2. The blocking defect, measured end to end

### 2.1 Reproduction

The production database holds 22 orders, so the defect is invisible there. A branch
was provisioned with the **exact** RLS policies, helper functions and indexes copied
verbatim from production, then seeded with **100 tenants × 1,000 orders = 100,000
work orders**, 1,000 auth users, 3,000 doctors, 1,000 clinics.

### 2.2 The scaling curve — linear, and measured at three points

Query: `select status, delivery_date from work_orders where status <> 'iptal'`
(this is [`LabDashboardScreen.tsx:1100`](../modules/dashboard/screens/LabDashboardScreen.tsx#L1100)),
run as `role authenticated` with a real lab-manager JWT.

| Total rows (all tenants) | Execution | Buffers | Rows returned | ms/row |
|---|---|---|---|---|
| 10,000 | **1,076 ms** | 149,762 | 100 | 0.1077 |
| 50,000 | **5,006 ms** | 708,569 | 500 | 0.1001 |
| 100,000 | **10,749 ms** | 1,407,077 | 1,000 | 0.1075 |

**Slope: 0.1075 ms per row, essentially perfectly linear.**

Note what those rows-returned figures mean: at 100,000 rows the query scans
**100,000 rows to return 1,000**. Cost is driven by *total rows across all tenants*,
not by the caller's own data. One large tenant slows down every other tenant.

For comparison, the same query with RLS bypassed at 100,000 rows:

| Role | Plan | Execution | Buffers |
|---|---|---|---|
| `postgres` | **Index Only Scan** `idx_work_orders_lab_status_date` | **2.8 ms** | 37 |
| `authenticated` | **Seq Scan** | **10,749 ms** | 1,407,077 |

**3,839× slower. 38,029× more I/O.** The index exists and is perfectly suited; RLS
makes it unusable because `lab_id = get_my_lab_id()` sits inside an OR branch.

### 2.3 Where it becomes a hard outage

`authenticated` carries **`statement_timeout = 8s`** (verified on production:
`pg_roles.rolconfig`). At the measured 0.1075 ms/row:

```
8,000 ms ÷ 0.1075 ms/row ≈ 74,400 rows
```

**Above ~74,000 total work orders, the dashboard query cannot complete.** Verified —
this is the actual error at 100,000 rows:

```
ERROR: 57014: canceling statement due to statement timeout
CONTEXT: SQL function "is_clinic_admin" statement 1
```

And over HTTP, as a real authenticated user:

| Request | Result |
|---|---|
| `GET /work_orders?select=status&status=neq.iptal` (dashboard, L1100) | **HTTP 500 in 8.27 s** — `57014 statement timeout` |
| `GET /work_orders?select=id&status=eq.uretimde` (badge count — **16,960 calls** in production telemetry) | **HTTP 500 in 8.26 s** |
| `GET /work_orders?…&limit=50` (paginated list) | HTTP 200 in **1.10 s** |

Even the *paginated* query takes 1.1 seconds, because RLS still evaluates rows until
it finds 50 the caller may see.

74,000 orders ≈ **15 labs** at the reference volume of 5,000 open orders each. Not 100.

## 3. The fix, measured

Applied on the branch: the four permissive SELECT policies on `work_orders`
consolidated into one, with helper calls wrapped in `(select …)` so they become
InitPlans instead of per-row calls ([`db-optimizations.sql`](db-optimizations.sql) §P0).

### 3.1 Query level

| | Before P0 | After P0 | Improvement |
|---|---|---|---|
| Execution (100k rows) | **10,749 ms** | **41.3 ms** | **260×** |
| Buffers | **1,407,077** | **3,024** | **465×** |
| Helper function calls | once **per row** | once **per query** (InitPlan) | 100,000× |
| Planning time | 7.16 ms | 4.07 ms | 1.8× |

The plan after the fix shows every helper collapsed to `InitPlan … (actual rows=1 loops=1)`.

### 3.2 HTTP level — same three requests

| Request | Before P0 | After P0 |
|---|---|---|
| Dashboard pipeline | **HTTP 500** in 8.27 s | **HTTP 200** in **0.358 s** |
| Badge count | **HTTP 500** in 8.26 s | **HTTP 206** in **0.317 s** |
| List, limit 50 | HTTP 200 in 1.095 s | HTTP 200 in **0.252 s** (4.3×) |

### 3.3 Tenant isolation — unchanged and verified

The whole risk of a policy consolidation is that it widens visibility. It did not:

| Check | Result |
|---|---|
| Distinct `lab_id` values visible to one lab user across 1,000 rows | **1** ✅ |
| `multitenant.js`, 20 tenants × 10 users, 2,404 requests | **0 violations** ✅ |
| **Active cross-tenant probes** (deliberately requesting another tenant's rows) | **222 issued, 0 leaked** ✅ |

### The second wall: unbounded dashboard queries

**P0 alone is not sufficient.** With it applied, the dashboard still misses its SLO by
8× at only 20 concurrent users. The suite pinpoints why:

| Signal | Measured |
|---|---|
| Requests per dashboard load | **12** (N+1 — analysis §2.3) |
| Payload per dashboard load | **250.7 KB** for a single 1,000-order tenant |
| Max rows returned in one flow | **2,000** |

At the reference tenant size (5,000 open orders) that payload becomes **~1.25 MB per
dashboard open**, on every app launch and every foreground resume. This is the
`P1: replace unbounded dashboard queries with server-side aggregate RPCs` item, and
the measurements say it is not optional.

## 5. Fixes applied to production

### ✅ P1 — foreign-key indexes (SHIPPED, COMPLETE)

**All 143 unindexed foreign keys are now indexed. Remaining: 0.**

| Metric | Before | After |
|---|---|---|
| Unindexed foreign keys | **143** | **0** ✅ |
| Invalid indexes | — | **0** ✅ |
| `work_order_photos` lookup by `work_order_id` | **Seq Scan** (5,297 seq scans / 125 rows) | **Index Scan** ✅ |

Applied in two passes:

1. **33 hot-path indexes** via `CREATE INDEX CONCURRENTLY` (no lock, no downtime) —
   `work_order_photos`, `status_history`, `order_messages`, `work_orders` (7 FKs),
   `order_stages`, `order_items`, `stage_photos`, `stage_material_selections`,
   `notifications`, `activity_logs`, `fifo_layers`, `fifo_allocations`,
   `support_tickets`, `payment_submissions`, `payment_intents`.
2. **110 remaining indexes** in one migration with plain `CREATE INDEX` — every
   affected table is small (largest 572 rows), so the lock was sub-millisecond.

Why the audit-column FKs matter too: when a parent row is deleted, Postgres scans
**every** child table referencing it. With 110 unindexed FKs mostly pointing at
`profiles`/`labs`, one account deletion meant 110 sequential scans — and the
KVKK-mandated `delete-account` edge function walks exactly that path.

⚠️ **Follow-up:** review `pg_stat_user_indexes` in a few weeks. There were already 64
unused indexes before this change; this set is subject to the same scrutiny, and
unused indexes are write amplification.

`idx_work_orders_lab_created` was deliberately **not** created — it would sit unused
until P0 makes `lab_id` sargable, exactly as `idx_work_orders_active` does today.

### ✅ P0 — RLS consolidation (SHIPPED 2026-08-02)

`work_orders` SELECT policies: **4 permissive → 1**. Helper calls wrapped in
`(select …)` so they evaluate **once per query** instead of once per row.

Production plan, same query, real lab-manager JWT:

| | Before | After |
|---|---|---|
| Execution | 2.950 ms | **0.931 ms** (3.2×) |
| Buffers | 310 | **13** (24×) |
| Planning | 5.71 ms | 3.95 ms |
| Helper calls | per row | **InitPlan — once** |
| `work_orders` policies | 11 total / 4 SELECT | **8 total / 1 SELECT** |

The absolute numbers are small because production holds 22 orders. The structural
change is what matters: helper cost is now **O(1) per query instead of O(rows)** —
which is the 260× measured at 100k rows on the branch.

**Visibility verified per user type against live RLS, not just predicted:**

| User type | Expected | Actual |
|---|---|---|
| lab / technician | 19 | **19** ✅ |
| doctor | 15 | **15** ✅ |
| clinic_admin | 15 | **15** ✅ |
| admin / manager (**second lab**) | 3 | **3** ✅ |
| clinic_admin with no orders | 0 | **0** ✅ |

The second lab's admin sees **3, not 19** — cross-tenant isolation intact.
Total visible (user, order) pairs: **210 before = 210 after.**

### ✅ P1 — dashboard aggregate RPCs (SHIPPED 2026-08-02)

`dashboard_pipeline_counts()` and `dashboard_activity_series(int)` move the
aggregation server-side. Return size is independent of order count: 3 status rows
and 7 series rows today, ~10 and ~13 at any scale.

Tenant guard verified by execution, not by inspection:

| **second lab's** admin | 3 ✅ (isolated) |
| doctor | **0 rows** ✅ (guard blocks) |
| clinic_admin | **0 rows** ✅ (guard blocks) |

**Client wired up** in `LabDashboardScreen.tsx`, with a fallback to the old queries
if the RPC is absent or errors:

| | Before | After |
|---|---|---|
| Unbounded queries per dashboard load | **2** | **0** |

## 6. Other measured findings (production)

| Finding | Evidence |
|---|---|
| **Realtime is 72 % of all database time** | 1,088,313 walrus calls, 5,720,075 ms of 7,941,022 ms total — with 1 tenant and 22 orders. Max single call **5,572 ms**. |
| **Only 24 of 60 connections free at idle** | 36 already consumed by Realtime/PostgREST/GoTrue/Storage/cron. A dashboard load issues 13–15 concurrent requests. |
| **PostgREST schema reloads — 2,082 times, ~672 s CPU** | **Investigated and downgraded.** No application function issues runtime DDL (checked all 401 for `CREATE TEMP` / dynamic `CREATE` / `ALTER` / `DROP` — zero hits). The only trigger is Supabase's stock `pgrst_ddl_watch` on `ddl_command_end`, i.e. **migration deployments**. Confirmed empirically: 143 `CREATE INDEX` statements applied today produced only ~11 reloads (2,071 → 2,082), so PostgREST debounces heavily. This is amortised deployment cost across the project's history, **not an ongoing production latency source.** Priority dropped from P2 to informational. |
| **Order create fires 13 triggers** | ~37 `activity_logs` rows per order (600 rows for 22 orders), all inside the user's transaction, cascading to `pg_net` HTTP calls with no queue, retry or DLQ. |
| **Advisor debt** | 655 WARN: 512 `multiple_permissive_policies`, 143 `unindexed_foreign_keys`, 142 `auth_rls_initplan`, 64 `unused_index`. |
| ~~Upload path holds 2.33× file size in RAM~~ | **Corrected and fixed 2026-08-02.** The original claim (200 MB STL → ~466 MB RAM → OOM; 6 of 7 sites unguarded) was **wrong**. There are 19 call sites; only `lib/photos.ts` used base64 and it was already capped at 5 MB, and the high-traffic paths already stream via `FormData`/XHR with 100 MB guards. Two real gaps found and closed: the pointless base64 round-trip, and two paths with no size cap. See analysis §5. |
| **Repo migrations do not replay from scratch** | Branch creation reported `MIGRATIONS_FAILED` with 0 of 310 applied — the Supabase Git integration is not connected. Disaster recovery currently depends on the live database, not the migration history. |
